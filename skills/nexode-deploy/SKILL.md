# Deploy on Nexode

Use the Nexode MCP tools. The MCP process reads `NEXODE_API_KEY` from the user's environment; never request the key in chat, print it, put it in source control, or place it in tool arguments.

A configured valid key is sufficient to operate Nexode within its permissions and plan limits. Verify it with `nexode_me` and use MCP directly. Do not request Nexode/Google login, dashboard access, passwords, cookies, session JWTs, SSH or Dokploy credentials. If the key is not configured, ask the user to set `NEXODE_API_KEY` in the MCP environment and restart the client. If invalid/expired/revoked, ask for a replacement configured the same way; if a scope is missing, identify that permission. Never fall back to website login or scraping for an API authentication error.

For a deployment of local app code, prepare the repository before cloud provisioning. For read-only checks or managed database/n8n operations, skip local code preparation.

Before the first deployment, ask what the project is called unless the user already supplied the name. Use that name for the app, not a repository name with generated suffixes. `nexode_compute_create` requires `app_id` and chooses clean names by default: `project.nexode.app` for `app_role: landing`, `dashboard-project.nexode.app` for frontend, and `api-project.nexode.app` for backend. Use a single DNS label for default URLs: nested names require additional TLS coverage and must never be selected implicitly or by disabling the DNS proxy. Pass roles explicitly and reuse the app's reserved namespace. An explicit `custom_domain` takes precedence; `subdomain` can override the default with one or two DNS labels. If the base is occupied/reserved, ask for an alternative rather than adding random suffixes.

For older deployments, change names only when requested. Inspect `nexode_apps` and compute list/get, resolve the actual service roles, and call `nexode_compute_rename_subdomain` with `nombre-del-proyecto`, `dashboard-nombre-del-proyecto`, or `api-nombre-del-proyecto`; rename the landing first. The key needs `compute:write`. The backend reserves the namespace for the app, preserves port/HTTPS route options and infrastructure identity, and rejects collisions. It replaces old URLs without redirects and does not rebuild code. Inspect and repair affected API URLs, CORS, auth callbacks, webhooks and build-time/source URLs as part of an authorized migration; preserve paths and unrelated values. Do not guess variable names or expose secrets. Rebuild affected services when URL configuration requires it. Verify each exact public URL through normal DNS and HTTPS, including nested names: a `*.nexode.app` certificate does not cover `dashboard.nombre-del-proyecto.nexode.app`. Reuse existing platform DNS; do not request DNS-provider login or claim success before certificates and dependent connections work.

1. Read [container-preflight.md](references/container-preflight.md). Inspect the real stack and selected service, call `nexode_deployment_requirements`, create a compatible production `Dockerfile` if absent, and align the actual listener with Nexode's host/port (frontend/landing 3000, backend 4000 by default). Preserve a compatible existing Dockerfile. Build and smoke-test when Docker is available. Commit only deployment changes and push using the user's configured local Git as part of the authorized deployment; verify the remote SHA. Adapt to the actual runtime and monorepo structure rather than assuming Node.js. Do not ask the user to manually write the Dockerfile or commit it when local tools and Git access are available.
2. Call `nexode_me`, `nexode_plans`, and `nexode_subscriptions` to check identity, scopes, and available slots. New Nexode API keys have full MCP permissions by default; customized or older keys may have narrower scopes. Superadmin accounts may bypass subscription checks; the Nexode backend remains the authority.
3. Use the repository URL already supplied by the user or the local Git remote. Call `nexode_repositories` only when repository discovery is needed. Reuse the existing provider connection. If GitHub is missing and the user authorizes connecting their local account, call `nexode_github_connect_local`: it reads the existing `gh auth token` internally and sends it only to the official Nexode HTTPS API. It returns only the GitHub identity, never the credential. If gh is not authenticated, ask the user to run `gh auth login`; SSH-only Git setup cannot provide an API credential. A different existing Nexode GitHub identity must be disconnected explicitly before replacement. For GitLab, request a provider connection only when missing; do not request a new Nexode login as a routine deployment step. The Nexode key authorizes Nexode operations, while local Git push and private repository access retain their existing provider credentials.
4. Call `nexode_apps` to select the app and workspace; use `nexode_app_create` if needed. Pass its `app_id` to every compute, database and n8n creation, and `app_role: landing` for the landing compute. A workspace holds one app; its team can view its visual services. `nexode_app_update` changes the grouping or workspace without rewriting variables. Inspect `nexode_apps` afterward to verify all cards and manually configured connections; values remain private. Use `nexode_app_connect` only when actually wiring/redeploying services is requested. Prefer an existing compute instance if the app is already deployed; use `nexode_compute_redeploy` after pushing. Otherwise call `nexode_compute_create` with provider, URL, branch, frontend/backend type and the explicit port verified during preparation. Nexode assigns a free subscription slot automatically; no tier selector is needed. For full stack apps, use separate compute slots. Add a database or n8n only when requested or required by the app. When the backend needs object storage, set `connect_storage: true` on creation so its private S3 credentials are in place before the first deployment. For an existing backend, call `nexode_compute_link_storage` and redeploy when its response says `redeploy_required: true`. The key needs `compute:write` and `storage:connect`; `nexode_storage_get` needs `storage:read`. Never put S3 credentials in frontend computes or source code.
5. Poll `nexode_compute_deploy_status` and inspect `nexode_compute_diagnose`, `nexode_compute_deployments`, or `nexode_compute_logs` if provisioning fails. Report the generated or custom URL when available. Do not claim the app is live from a successful create response alone. For a branch or same-repository PR review, use `nexode_compute_create_preview`; its isolated environment has no production variables and expires automatically. Share its one-time basic-auth credentials privately. Use `nexode_compute_rollback` only when a retained rollback image is listed and the user approves reverting the live app.

Compute read tools omit stored passwords and environment content. Use `nexode_compute_set_env` to merge runtime variables, then redeploy. For a Nexode database, prefer `nexode_compute_link_database` so its URI remains server-side; the key needs `compute:write` and `databases:connect`. Never print, log, or commit secrets. Domain purchases require a separate Stripe checkout in a browser.

For database data, use `nexode_database_browse` to list tables or collections, then browse one in pages of 25. SQL rows appear as tables, MongoDB documents as JSON, and Redis as keys. To edit one value, pass the exact `primaryKey` fields from the browser result in `key` to `nexode_database_update_value`; MongoDB uses `_id`, Redis uses `key`. `nexode_database_delete_record` permanently removes one row/document/key. `nexode_database_delete_field` drops an SQL column from the entire table or unsets a MongoDB field in one document; include its `_id` in `key`. Confirm destructive targets and their impact with the user immediately before deleting. Do not use these tools on a different database than the one the user named.

For PostgreSQL, MySQL, and MongoDB backups, call `nexode_database_backups` first. Enable daily backups or run an immediate copy when needed. Before a live restore, run `nexode_database_test_restore` on the selected file; it restores into a temporary database and verifies access without touching live data. A live `nexode_database_restore` replaces data and needs the user's approval plus the exact database name in `confirmation`. Redis restore is not available yet.

For domains bought externally, first call `nexode_domains` to reuse an existing record. If absent, call `nexode_domain_add_external` with the domain name (requires `domains:write`); this saves it as pending, without purchasing or transferring it. Give the user the exact `verification.type`, `verification.name` and `verification.value` from the response to publish at their DNS provider, or apply that TXT through an available authorized DNS connection. `nexode_domain_get` retrieves a pending challenge later. Call `nexode_domain_verify_external` after publication and report activation only when the backend returns `active`; missing/mismatched TXT and propagation delays are still pending. Keep nameservers and existing mail records intact. Attaching a verified domain to the requested app/compute and configuring routing DNS are separate steps; use the actual Nexode target rather than guessing an IP. If DNS access is unavailable, provide the exact TXT and remaining steps so another agent or the user can continue without Nexode browser login.

When requested, configure wildcard routing at the existing DNS provider after getting the real Nexode DNS target. For Cloudflare, add A `@` and A `*` for a verified origin IPv4, or CNAME `@` and CNAME `*` for a verified direct routing hostname, with DNS only for initial origin HTTPS validation. Verify cross-account routing before using a target that already resolves to Cloudflare proxy IPs. Preserve mail, verification TXT and explicit subdomain records. Wildcard DNS covers names without explicit records; it does not attach them to services or provide wildcard HTTPS. Attach each hostname to its requested compute, then test HTTPS. Wildcard TLS needs separate DNS-01 certificate support; do not claim it is enabled just because DNS exists. Do not map all subdomains to the landing automatically.

For a frontend or commercial landing, also read [frontend-quality.md](references/frontend-quality.md). Verify responsive content before publishing and the actual public domain afterward. For an inaccessible site, distinguish DNS, public HTTPS, internal listener and the affected client before changing routing or ports.

For an authorized full-stack connection or hostname migration, inspect the actual source/runtime variable names and call `nexode_app_connect` with its `variables` mapping. Map frontend API, backend app/CORS, landing app and reverse landing links when those features exist. Names are persisted for reconnects; do not rely on guessed Next.js defaults for Vite, a server proxy, or another stack. Database and S3 values must stay backend-only. OAuth authorized domains (Firebase/Google) and signed payment webhook URLs are external provider configuration, not environment variables: update them separately through authorized access and verify a real login. Verify password login, Google login, CORS and session continuity, not health alone. Standard customers use the same scoped API; partner/admin access is not required.

For new frontend/landing deployments, include automatic web analytics unless the user opts out. Read [web-analytics.md](references/web-analytics.md): retrieve the exact script with `nexode_compute_analytics`, install it once in the real source, enable with `nexode_compute_configure_analytics`, then commit/push, redeploy and verify real visits. Existing sites are integrated when requested; preserve deliberate paused tracking during unrelated maintenance.
